论文图表规范手册

覆盖流程图、UML 六类图、E-R 图、数据流图与架构图的符号定义、绘制规则和正确／错误对照。所有样例统一使用订单与审核场景，可直接套用到各自的课题。

00通用规范

在讨论具体图形之前，有六条规则对所有图都成立。它们与图形语法无关，却几乎决定了评审对图表专业度的第一判断。

图号、题注与正文引用

  • 按章编号：图 3-1、图 4-2，章内连续，全文不重号。跨章不要用"图 12"这种连续编号。
  • 题注在图下方，居中，与图之间留 6pt，格式为「图 4-2　系统部署图」。表题注在上、图题注在下，这条最容易搞反。
  • 图内不写标题。标题已经在题注里了，图里再放一次属于重复。
  • 先引后出：正文必须先出现"如图 4-2 所示"，图才能跟在后面，不能反过来让读者自己找。
  • 一图一主题。一张图讲两件事，就该拆成两张。
  • 来源标注：作者自绘写"资料来源：作者绘制"；引用他人须注明出处。
图 形 区 域
图 4-2　系统部署图
题注居中、位于图下方、与图间距 6pt

字号、灰度与清晰度

  • 图内文字不小于正文的 70%。正文小四（12pt）时，图内文字不小于 8.5pt，通常取 9–10.5pt。
  • 黑白可辨：论文默认黑白打印，不要用颜色承载语义（"红色表示失败"在灰度下消失）。靠线型、形状、文字标注区分。
  • 导出矢量。SVG / EMF / PDF 优先，PNG 次之，且不低于 300 dpi。禁止直接截图——截图在打印时会糊成一团。
  • 框内文字要能读完。字号压到 6pt 才能塞下的内容，说明该拆图，而不是该缩字。
一条自检办法：把整页缩到 50% 看一遍。如果此时线条糊成灰块、文字看不清，那它印在纸上就是这个效果。
怎么套用到自己的课题：把样例里的"用户""订单""审核"换成你系统里的实体，图形结构不用动。判断一张图合不合规，看的是形状、连线、标注，与业务内容无关——这也是本手册能通用到任何课题的原因。

01流程图

依据 GB 1526-89 / ISO 5807:1985。这是国标里唯一给出完整流程图符号体系的标准，也最容易被评审对照检查。

1.1 符号定义GB 1526-89 §4

国标规定的符号是固定形状，不是风格选项。十个常用符号如下：

终止符
开始 / 结束 / 暂停
处理
赋值 / 计算 / 动作
判断
条件分支
输入 / 输出
数据的读入与输出
文档
打印 / 纸质文档
预定义处理
调用已定义子流程
连接符
跨页 / 断线接续
人工操作
须由人执行的动作
存储数据
数据库 / 文件
注释
补充说明，不参与流程
关于起止符的争议只有一个答案：国标里它叫"终止符"，形状是两端半圆的扁长形（跑道形），矩形四角不能只倒一点圆角。很多绘图工具默认给你一个"圆角矩形"，那不是终止符，只是处理框的装饰版。

1.2 绘制规则GB 1526-89 §5

  • 处理框单入口、单出口。一个框拉出两根线，读者就得猜哪根是主流程。
  • 判断框单入口、多出口，每个出口必须标条件（是／否，或具体取值区间）。不标条件的菱形等于没画。
  • 流向自上而下、自左而右。回退、循环等逆向流才允许由下往上，且必须画成明确回跳线。
  • 尽量避免交叉线。必须交叉时，在交叉处画一个跨线小弧，否则会被读成连接点。
  • 多线汇合处画实心小圆点，或者让各分支独立连到目标框，不要"搭"在别人的线上。
  • 流程图只写业务动作。数据库字段值、代码变量、接口路径属于实现细节，放注释或正文，不进框。

1.3 正确与错误对照

同样是"金额阈值判断"这段逻辑，下面两版放在一起看，差别一目了然。

符合 GB 1526
四个关键点：终止符为跑道形；菱形两出口都标了条件；两分支在汇合点打了实心圆点；框内只有业务动作。
常见错误
四处问题：① 起止用圆角矩形，两套规范都不认；② 菱形出口没标条件；③ "自动通过"的线斜穿左侧连线，形成交叉且无跨线弧；④ 汇合点无标记，读起来像临时搭接。
最常被扣分的一条：把数据库字段值写进流程图。status 设为 3 这种写法说明画图时在想实现，而不是在想流程。改成"记录状态置为待审核"，字段值留到正文的数据字典里说。

02UML 图形

依据 UML 2.5.1。UML 与国标流程图是两套独立的语法，起止符号、动作框形状都不同。同一篇论文里只能选一套，混用是评审最容易识别出的问题。

先把路线定下来：同一篇论文里，流程类图只能认一套语法。走 UML，就全篇实心圆起、带环圆止；走国标流程图，就全篇跑道形终止符。两套各自都合规，混在一起才是错——评审未必会因为"没按国标"扣分，但一定会因为"前后不一致"怀疑你没想清楚。

论文里该画哪几张

图种必要性放在哪一章典型内容
用例图必画需求分析每个角色一张，或合并成一张总图
类图建议（可按模块拆）系统设计核心业务实体与接口抽象
时序图必画 1–2 张核心流程系统设计或实现登录、下单、审批等主链路
活动图必画 1–2 张系统设计带分支、并发或异常处理的业务
状态图有状态机就画系统设计订单、工单等有流转过程的对象
部署图必画系统设计客户端 / 应用服务器 / 数据存储
组件图、包图可选概要设计不画不影响完整性
数量控制：论文的图不是越多越好。8–12 张核心图，每张都能说清一件事，比堆 25 张截图强。同一个流程不要既画活动图又画时序图又贴界面截图——选一个最能说明问题的。

2.1 用例图Use Case Diagram

回答"系统给谁用、能做什么"。它不表达顺序，这是最容易画错的地方。

元素与语法

  • 参与者：小人图形，名称写在下方。放在系统边界外侧。
  • 系统边界：矩形框，系统名写在框内顶部。所有用例必须在框内。
  • 用例：椭圆，名称写动宾结构——"提交订单""申请退款"，不是"订单功能""步骤一"。
  • 关联：参与者与用例之间画实线 + 箭头，箭头指向用例，表示"由谁发起"。UML 规范里这个箭头是可选的（导航性），但教材与论文普遍都画，画了更直观——关键是全篇一致，别一张画一张不画。
  • 包含「include」：虚线箭头，指向被包含的用例。箭尾是主动方。
  • 扩展「extend」：虚线箭头，指向被扩展的用例（即基础用例）。方向最容易反。
  • 分层排布：主用例排一列，被 include / extend 的用例整体右移一列并上下错开，连线自然呈扇形。全堆在一列会让 include 关系看不出来。
  • 泛化：实线 + 空心三角，指向父参与者／父用例。
规范画法
要点：参与者在外、用例在内；用例名是动宾短语；关联线箭头指向用例；include 箭头指向被包含用例，extend 箭头指向基础用例；被包含用例整体右移一层，层级一眼可见。
常见错误
两处问题：① 用例被连成流程，暗示"先下单再计价再支付"——用例图不表达顺序，顺序归活动图或时序图；② 参与者画进了系统边界内，边界就失去了"系统职责范围"的含义。
include 和 extend 的方向：记住一句话——箭头永远指向"被依赖的那一个"。提交订单 ..> 计算优惠（include，下单必然要算优惠）；导出订单 ..> 查看订单（extend，导出是可选的扩展）。搞反了会把"必要步骤"说成"可选功能"。

2.2 类图Class Diagram

类图的价值全在关系符号上。框画得再漂亮，菱形画反了这张图就是错的。

六种关系的线型

关系符号含义常见例子
关联结构上的连接用户 —— 订单
聚合整体-部分，可分离班级 ◇— 学生
组合整体-部分，同生共死订单 ◆— 订单项
泛化继承（is-a）管理员 —▷ 用户
实现实现接口订单服务 —▷ 支付接口
依赖临时使用控制器 ---> 服务

类框写法

  • 三层矩形：类名 / 属性 / 方法，中间用横线分隔，类名居中且首字母大写。
  • 可见性符号写在成员前：+ public、- private、# protected、~ package。
  • 格式为 可见性 名称: 类型，如 - confidence: BigDecimal。
  • 接口标注 «interface»，抽象类类名用斜体。
  • 菱形永远画在"整体"那一端。订单包含订单项 → 菱形贴着订单，不贴订单项。
规范画法
要点：三层结构清晰；可见性符号齐全；多重性标在线两端；组合菱形贴着 Order（整体端）。
常见错误
三处问题：菱形方向反、成员缺类型与可见性、多重性缺失。
聚合 vs 组合的判断方法：问一句"整体没了，部分还活着吗"。订单删了，订单项跟着删 → 组合（实心）。班级解散了，学生还在 → 聚合（空心）。这个判断比记符号可靠。

2.3 时序图Sequence Diagram

按时间顺序讲一次调用是怎么发生的。四个符号定生死：实心箭头＝同步、开放箭头＝异步、虚线返回、激活条。

元素与语法

  • 参与者框在顶部，从左到右按调用发生的先后排列，不要为了美观乱序。
  • 生命线：参与者下方的虚线，表示该对象存在的时段。
  • 激活条：生命线上的窄矩形，表示对象正在执行。没有激活条就分不清谁在处理。
  • 同步消息：实线 + 实心箭头，表示调用并等待返回。
  • 异步消息：实线 + 开放箭头（V 形），表示发出去不等结果。
  • 返回消息：虚线 + 开放箭头。用实线画返回是最常见的错。
  • 组合片段：alt（分支）、opt（可选）、loop（循环）、par（并发），左上角五边形标签，每个分支写 [条件]。
规范画法
要点：同步调用用实心箭头；返回用虚线与开放箭头；订单接口与支付服务都有激活条，能看出各自在处理哪一段。
常见错误
三处问题：① 返回消息用了实线实心箭头，与调用无法区分；② 全文没有激活条，看不出谁在处理；③ 消息名写成 submit(OrderDTO)，这是代码不是业务动作。
论文里的时序图要"业务化"：消息名写"提交订单""调用支付""返回订单号"，不写方法签名。评审关心的是系统怎么协作，不是 DAO 叫什么。

2.4 活动图Activity Diagram

活动图和国标流程图长得很像，符号却完全不同。混用等于两套规范都没遵守，而且是最容易被一眼看出的那类问题。

先分清三种"流程类"图

图种回答什么问题起止符号节点的含义
流程图
GB 1526		处理步骤与数据怎么流跑道形终止符处理动作
活动图
UML		控制流怎么走、哪里并发实心圆 / 带环实心圆动作（Action）
状态图
UML		一个对象经历过哪些状态实心圆 / 带环实心圆状态（State）

起止节点：三套画法对照

GB 1526 流程图
两端半圆的跑道形，框内写"开始"/"结束"。
UML 活动图
实心圆起、带环实心圆止，且不写任何文字。
两套都不认
圆角矩形 + 文字。既不是终止符，也不是初始节点。
为什么这个错特别扎眼：圆角矩形在 UML 里是动作框的规范形状。用它写"开始"，等于告诉读者"这是一个动作，名字叫开始"。语义完全错了。

完整活动图

包含初始节点、动作、决策、终止节点四个要素，外加条件标注与汇合点：

规范画法
要点：初始节点无文字；动作框是圆角矩形；菱形出口标条件；分支汇合处画实心圆点；终止节点带外环。
常见错误
三处问题：① 起止用圆角矩形写文字；② 菱形出口没有条件是／否；③ 汇合点没画实心圆点，两根线像直接撞在上面。
分叉与汇合不能用菱形：并发分支用粗黑横线（fork/join bar），不是判断菱形。菱形只表示"二选一或几选一"，粗线表示"同时都走"。这两个混了，并发语义就丢了。

2.5 状态图State Machine Diagram

只描述一个对象在不同状态之间怎么迁移。它和活动图最核心的区别：活动图的节点是"做什么"，状态图的节点是"处于什么状态"。

元素与语法

  • 状态框：圆角矩形，名称用形容词或动名词——"草稿""待审核""已发布"，不用"提交申请"这种动作。
  • 转移：实线箭头，标注格式 事件[守卫条件]/动作，如 提交[材料齐全]/受理。
  • 初始与终止：与活动图相同，实心圆与带环实心圆，无文字。
  • 每个状态必须可达，不能有孤立的状态；除终态外，每个状态应有出边。
  • 状态数量控制在 5–9 个。超过就要拆成复合状态，否则图会变成蜘蛛网。
规范画法
要点：状态名是"草稿／待审核／已发布"这类状态词；每条转移都标了事件或条件；撤回修改画成明确的回边。
常见错误
两处问题：① 状态名用了动词短语（"提交申请""写入数据库"），这是动作不是状态；② 所有转移都不标事件，读者不知道什么条件下会迁移。
判断方法：如果框里的文字能接在"当前处于——"后面（当前处于待审核、当前处于已发布），那是状态；如果接的是"系统要——"（要提交、要调用），那是动作，该放活动图。

2.6 部署图Deployment Diagram

说明软件跑在哪些物理或虚拟节点上、节点之间怎么通信。节点必须画成立体盒，这是 UML 给它的专属形状。

元素与语法

  • 节点（Node）：立体盒（正面矩形 + 顶面平行四边形 + 侧面平行四边形），标注 «device» 或 «executionEnvironment»。
  • 构件（Artifact）：节点内的矩形，标 «artifact»，写实际部署物名称（app.jar、nginx.conf）。
  • 通信路径：节点之间画实线，标注协议——HTTPS、JDBC、Bolt。
  • 数据库：圆柱体，或节点内标注 «database»。
  • 外部依赖（对象存储、第三方 API）放在节点之外，用云形或独立盒子表示。
规范画法
要点：立体盒体现"物理节点"的含义；内部构件标明具体部署物与端口。
常见错误
问题：用平面矩形画节点，和普通类框、组件框没有区别，读者无法判断这是"运行环境"还是"逻辑模块"。
别把部署图画成分层架构图：部署图的组织维度是机器／运行环境（客户端、应用服务器、数据库服务器），不是逻辑分层（表现层、业务层、数据层）。想讲分层就单独画架构图。

03E-R 图

数据库设计章节的核心图。先选定记法，再画——陈氏记法和 IE 鸦脚记法不能混用，这是 E-R 图最常见的问题。

两种记法

记法实体联系属性适用场景
陈氏（Chen）矩形菱形椭圆概念模型、教学、答辩讲解
IE 鸦脚（Crow's Foot）表框（含字段）连线 + 端点符号表内字段行物理模型、工程文档

IE 鸦脚能同时表达字段、主外键和基数，信息密度高，更适合工程文档。一旦选定就全图统一鸦脚，不要再出现菱形。

鸦脚端点符号

双竖线
竖线 + 圆
三叉（鸦脚）
竖线 + 鸦脚
规范画法
要点：表框含字段与类型；主外键显式标注；关系线两端都标基数；一张图只用一个记法。
常见错误
两处问题：① 菱形（陈氏）与表框（鸦脚）混用；② 关系线两端都没有基数标注，等于只说了"有关联"，没说"怎么关联"。
跨库关联要标出来：当业务库与图库、文档库分属不同存储引擎，跨库字段（如 graph_id、entity_name）无法设物理外键。这类关联用虚线画，并在图注里说明"由应用层保证一致性"——这比假装有外键诚实，也更容易得分。

04数据流图

依据 GB/T 1526 系列。DFD 讲的是数据在系统里怎么流动、被什么处理、存到哪里，它不表达控制流（没有判断、没有循环）。

四个符号

外部实体
系统之外的数据源或去向
处理
圆角矩形，编号 + 动词
数据流
箭头，必须标数据名
数据存储
右开口矩形，编号 D1、D2

绘制规则

  • 自顶向下分层：顶层图（1 个处理）→ 0 层图（主要处理）→ 1 层图（细化的子处理）。每层必须输入输出平衡，父图的输入输出在子图里要能对上。
  • 处理必须有编号（1、2、3 或 1.1、1.2），名称用"动词 + 名词"。
  • 每个处理至少一个输入和一个输出。只有输入没有输出叫"黑洞"，只有输出没有输入叫"奇迹"，都是硬伤。
  • 两个处理之间不能直接连线，中间必须经过数据存储或外部实体。
  • 数据流必须标名字，不能只画一根光秃秃的箭头。
DFD 不画判断菱形：看到条件分支就说明你在画流程图，不是数据流图。DFD 只关心"什么数据、从哪来、到哪去、被谁处理"。

05架构图

架构图没有国标，但有一条隐含共识：它表达的是逻辑分层，不是物理部署。

分层架构图
要点：层与层之间边界清晰；每个方框标了具体技术而不是空泛的"服务层"；同层元素对齐排布。
常见问题
  • 方框只写"业务层""数据层"，没有具体技术栈——评审看不出你到底用了什么。
  • 把部署图当架构图画，画了一堆服务器和箭头，读者看不出分层。
  • 层内元素不对齐，大小不一、间距随意，看起来像草图。
  • 箭头双向乱指。依赖方向应单向自上而下，跨层调用才允许例外并加注。
  • 一张图塞 30 个框。超出一屏就该拆成"总体架构 + 模块详图"。

06工具与导出

工具选对了，规范问题一大半会自己消失——因为标准符号是内建的，不必逐个手动画。

推荐组合

用途工具理由
UML 各类图PlantUML符号由语法保证，不会画错形状；可版本管理；纯文本好改
需要精调版式draw.io / Visio图形库内置标准符号，可导出 SVG / EMF
快速原型ProcessOn在线协作方便，但导出质量一般
最终排版Word / LaTeX插入矢量图，不要插图床截图

PlantUML 关键配置

三行 skinparam 就能保证灰度可读、无阴影、字体一致：

skinparam monochrome true
skinparam backgroundColor #FFFFFF
skinparam shadowing false

活动图的正确骨架（注意 start / stop 会自动渲染成实心圆与带环实心圆，不必自己画）：

@startuml
start
:接收订单请求;
if (金额 < 500 ?) then (是)
  :转人工审核;
else (否)
  :自动通过;
endif
stop
@enduml

用例图的 include / extend 方向，记法就是"箭头指向被依赖方"：

F1 ..> F1a : <<include>>   ' 提交订单 依赖 计算优惠
F2a ..> F2 : <<extend>>    ' 导出报告 扩展 查看记录

导出设置

  • 优先 SVG 或 EMF。Word 里插入 EMF 可无损缩放，打印不糊。
  • 必须用 PNG 时加 -DPLANTUML_LIMIT_SIZE=8192 放宽尺寸上限，否则大图会被截断。
  • PNG 分辨率不低于 300 dpi；整页宽度的图，像素宽度不低于 2000px。
  • 导出后转灰度看一眼：如果两条不同含义的线变成同一种灰，就得改线型。
  • 文件名与图号对应（fig4-4-triage.svg），后期改图不会找错。
别用截图当插图：把工具界面截图贴进 Word 是最省事也最扣分的做法。截图在 100% 缩放下看着还行，打印出来线条发虚、文字毛边。正确做法是导出 SVG 或 EMF 再插入——Word 里能无损缩放，放大到 200% 依然锐利。

定稿前 60 秒快检

不用逐条对表，做三个动作就能筛掉大部分问题。

第一步
页面缩到 50% 看一眼

线条糊成灰块、文字认不出的，印在纸上就是这个效果。

第二步
打印一张黑白的

两条不同含义的线如果变成同一种灰，就得改线型。

第三步
遮住所有图，只读正文

读不出每张图在讲什么，说明正文的引用句没写清楚。
